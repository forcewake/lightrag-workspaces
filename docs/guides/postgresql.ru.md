# PostgreSQL + VectorChord

Этот режим переносит данные LightRAG в PostgreSQL и сохраняет выбор workspace в обоих интерфейсах и API. Используются `PGKVStorage`, `PGDocStatusStorage`, `PGVectorStorage` с `VCHORDRQ` и `PGTableGraphStorage`. Для графа достаточно обычных таблиц PostgreSQL; Apache AGE не нужен.

[Полная инструкция и команды на английском](postgresql.md)

## Что переносится

В PostgreSQL переносятся документы, чанки, статусы, метаданные, сохранённые embeddings, сущности и связи графа, поддерживаемый кеш LLM. Сохранённые векторы импортируются без обращения к embedding-провайдеру. Столбцы `vector` сохраняют float32; качество приближённого поиска через индекс проверяется отдельно.

Кроме рабочих таблиц сохраняется отдельный архив `lightrag_workspace_archive` с исходными JSON-записями и метаданными графа/векторов. Старые форматы кеша приводятся к рабочему виду, а недостающие связи документов и графа восстанавливаются из сохранённых данных, где это возможно, без моделей. Удаление документа или повторная обработка через API не удаляют исторический архив миграции и резервные копии. Их хранение и удаление нужно учитывать отдельно.

Загруженные оригиналы и результаты разбора остаются в прежних папках `inputs/<workspace>`. Управляющие файлы регистрации, блокировки и логи тоже остаются на диске. Исходные JSON, NanoVectorDB и GraphML сохраняются отдельно для проверки и отката.

Неизвестные файлы хранилищ `kv_store_*.json`, `vdb_*.json`, `graph_*.graphml` и неподдерживаемые структуры GraphML останавливают перенос до публикации готовой регистрации: для них нужна явная адаптация. Другие файлы, например ZIP-архивы и дополнительные артефакты, остаются в исходной копии и резервном снимке. Отчёт перечисляет их пути в `retained_source_only_files` внутри каждого workspace и `retained_source_only_root_files` в корне источника. Эти файлы не становятся рабочими записями PostgreSQL; их нужно сохранять и резервировать отдельно.

Точные имена workspace не меняются. Имена с дефисами, точками и подчёркиваниями поддерживаются; внутренний namespace PostgreSQL вычисляется из SHA-256 точного имени. Например, `meeting-notes` и `meeting_notes` не объединяются.

## Подготовка

1. Завершите загрузки и остановите старый сервис. Сохраните проверенную холодную копию всех данных, `inputs`, пустых папок, настроек, точного образа и шаблона контейнера.
2. Создайте **новую отдельную пустую базу**. Не используйте базу другого приложения или существующего LightRAG. Установите pgvector и VectorChord; `vchord` должен быть предварительно загружен через `shared_preload_libraries`.
3. Включите `vector` и `vchord` только в новой целевой базе. Приложение не меняет общие настройки сервера и не перезапускает PostgreSQL.
4. Подготовьте новый пустой каталог управляющих файлов отдельно от исходных данных, `inputs` и runtime. Исходную копию при миграции подключайте только для чтения.
5. Сохраните прежнюю embedding-модель, размерность, провайдеров и настройки парсера. Одинаковая размерность не делает разные модели совместимыми.

Проверенная эталонная конфигурация: PostgreSQL 18.3, pgvector 0.8.2, VectorChord 1.1.1, embeddings на 3072 измерения. Подключение к БД должно работать из контейнера LightRAG. Если PostgreSQL находится в другом контейнере, используйте общую Docker-сеть либо доступный адрес и опубликованный порт; `localhost` внутри контейнера — сам контейнер.

## Настройки

Добавьте в приватный `.env`:

```dotenv
LIGHTRAG_STORAGE_BACKEND=file
POSTGRES_HOST=postgresql
POSTGRES_PORT=5432
POSTGRES_USER=lightrag
POSTGRES_PASSWORD=your-private-database-password
POSTGRES_DATABASE=lightrag_workspaces
POSTGRES_SSL_MODE=disable
POSTGRES_MAX_CONNECTIONS=4
POSTGRES_VECTOR_INDEX_TYPE=VCHORDRQ
POSTGRES_VCHORDRQ_EPSILON=2.3
POSTGRES_VCHORDRQ_PROBES=
POSTGRES_VCHORDRQ_BUILD_OPTIONS=
```

Оставьте файловый режим до завершения проверки переноса. `disable` подходит только для запланированного доверенного локального подключения; при TLS используйте нужный режим и сертификаты из конфигурации upstream. Пароли не передаются аргументами мигратора и не публикуются в репозитории.

Лимит `POSTGRES_MAX_CONNECTIONS` действует на каждый активный процесс. Шлюз использует ещё до двух подключений. Учитывайте это вместе с остальными приложениями PostgreSQL. `epsilon=2.3` без явного разбиения индекса — начальная настройка; для полного корпуса измерьте качество поиска и время запросов.

## Перенос

Мигратор входит в образ: `/opt/lightrag-multiworkspace/migrate_postgres.py`. У него три действия:

- `plan` — читает исходную копию, составляет план, не подключается к PostgreSQL.
- `apply` — импортирует, проверяет результат и только после успешной проверки публикует готовые регистрации workspace.
- `verify` — повторно проверяет источник и PostgreSQL без повторного импорта.

Проверка сверяет исходные файлы до и после переноса, исходные и рабочие записи после чтения из БД, побитовую сохранность float32-векторов, количества записей и валидность VCHORDRQ-индексов. Произвольные файлы, которым нет соответствия в выбранном backend, остаются в исходной копии; их нельзя удалять после одного успешного запуска приложения.

Во всех трёх командах указываются одинаковые `--source-root`, `--control-root`, `--target-database`, `--target-token`, `--embedding-model` и `--embedding-dim`. Токен — новый UUID для этой конкретной базы; сохраните его для возобновления и проверки. `--workspace точное-имя` можно повторять для выбора нескольких баз. Без него берутся все прямые дочерние папки. [Готовый пример команды](postgresql.md#plan-import-and-verify).

Старые `pending`, `processing` и другие незавершённые состояния сохраняются: такие workspace остаются защищены от изменений, поиск доступен. Ошибочные документы не запускаются заново автоматически. Ошибка проверки не должна превращаться в скрытое повторное обращение к модели: сначала сохраните источник и отчёт, затем определите отдельный шаг восстановления.

## Переключение установки

Остановите файловые процессы. Переназначьте `/app/data/rag_storage` на **новый каталог управляющих файлов**, сохраните прежний mount `inputs` и отдельный runtime. Поставьте `LIGHTRAG_STORAGE_BACKEND=postgres`, оставьте прежний `LIGHTRAG_DEFAULT_WORKSPACE` и запустите один шлюз.

Проверьте список всех workspace и количество документов, граф и поиск в нескольких базах, переключение в обоих интерфейсах, адреса `/workspaces/<id>/…`, заголовок `LIGHTRAG-WORKSPACE`, выбор по умолчанию и отказ для неизвестного имени. Настройки и история браузера привязаны к прежним публичным именам и сохраняются.

Шлюз сверяет управляющие файлы с идентичностью и регистрацией в PostgreSQL, а счётчики читает из живой БД. При недоступности или несовпадении целевой базы он блокирует доступ; старые JSON не используются как запасной источник.

## Новая база и откат

Для новой пустой базы создайте отдельную пустую исходную папку штатным `init_workspace.py`, затем выполните `plan`, `apply`, `verify` с `--workspace` и токеном уже используемой PostgreSQL-базы. Не пишите управляющие manifests вручную. API никогда не создаёт неизвестный workspace.

После переключения резервная копия должна включать согласованную копию PostgreSQL, управляющие файлы, `inputs`, приватные настройки и версию приложения. Сохраняйте также исходный файловый снимок. Проверьте восстановление отдельно от рабочей базы.

Откат к файлам возвращает состояние выбранного файлового снимка. Новые изменения PostgreSQL обратно в JSON автоматически не переносятся. Сначала остановите сервис, сохраните текущую БД и `inputs`, затем восстановите прежний образ, настройки и согласованную пару данных/inputs. [Подробности резервного копирования и отката](backup-and-rollback.md).
